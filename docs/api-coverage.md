# Capital.com API coverage audit

Audited 2026-11-12, before implementation. Sources: [official API reference](https://open-api.capital.com/), [development guide](https://capital.com/en-int/trading-platforms/api-development-guide). The reference embeds OpenAPI 3.0; its body schemas are mostly generic objects, so the field constraints below come from its parameter tables and response examples. No pagination parameters are documented; none will be invented.

All REST paths below include `/api/v1`. Auth: K = X-CAP-API-KEY; S = CST + X-SECURITY-TOKEN. Existing methods were inspected for actual HTTP behavior, including stubs. All existing GET wrappers unnecessarily send a JSON string body. Path interpolation and query concatenation need encoding; DEMO requests need the same rate limits as LIVE. Existing network failures latch the client; preserve this fail-closed behavior.

## Audit findings

- Session switch/logout, preferences/top-up, position update, working-order mutations, sentiment and five watchlist methods are stubs.
- Session creation supports plaintext only; encryptedPassword is missing. Logout must accept an empty successful response and clear tokens.
- Activity/transaction history lack all optional filters; prices lack from/to; category subnodes lack limit; /markets lacks search and no-query variants.
- Position creation lists all documented fields, but truthiness filtering loses explicit false values; invalid size/stop combinations are not validated.
- Existing LIVE open/close risk, ownership, durable intent and confirmation checks must remain authoritative. New LIVE mutations must fail closed where that risk model cannot validate their impact.
- Raw HTTP helpers must not become an alternative route around LIVE authorization. All errors/streaming events must avoid disclosing server-echoed secrets.

## Final implementation and verification status

All 36 REST operations are implemented and covered by offline route contracts. Of these,
33 were verified against DEMO. Account switch, preference update and balance top-up remain
broker-unverified because testing did not require changing account configuration. All
five WebSocket destinations have offline and DEMO verification, including quote, classic
OHLC and Heikin-Ashi event delivery in a separate stream check.

Initial statuses above describe the code before changes. New LIVE mutation impacts are
intentionally blocked pending dedicated risk policies; the existing guarded LIVE position
open/close path remains intact. This is full documented inventory coverage, not a claim
that every operation or parameter combination was exercised on a broker or enabled on LIVE.

Evidence was recorded locally in `docs/demo-api-verification.json` and
`docs/demo-api-readonly-verification.json`; generated reports are excluded from version
control. See [usage and limitations](api-usage.md) to reproduce verification.
All automated HTTP route tests use the official inventory fixture; broader failure,
